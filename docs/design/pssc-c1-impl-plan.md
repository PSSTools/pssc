Scope: Implement Phase C1 of `design/pssc-c-bridge-runtime-design.md` (Backend B,
first slice): a `zsp_bridge` runtime + a generated multi-action spawn dispatcher,
built into a `libpssc_scenario.so` and driven from SystemVerilog over DPI by a
minimal trampoline that just **spawns + runs to done**. **No imports** (C2+).

## Verification results (the gating unknowns — all green)

Spikes run 2026-06-19 in this environment (gcc 13.3, Verilator 5.041):

1. **Generated action API.** `c-host` emits, per action, exactly the spawn
   primitives we need: `void <Action>_init(zsp_init_ctxt_t*, <Action>*, const
   char* name, zsp_component_t* parent)` and `void <Action>_body(<Action>*,
   zsp_timebase_t*)`. The existing `sw_tgt._root_harness` already calls these for
   one root; C1 generalizes to an N-action switch.
2. **C runtime builds + runs.** `gcc -I<be-sw/share/include> -I<out> <generated>.c
   <be-sw/share/rt>/*.c -o sim` builds and runs (exit 0).
3. **Shared object.** `gcc -fPIC -shared` produces a `.so` cleanly
   (`compile_shared` in `zuspec.be.sw.compiler` wraps this).
4. **DPI from a `.so` on Verilator.** A `.so` of `import "DPI-C"` functions links
   into a Verilator `--binary` build via
   `-LDFLAGS "-L<dir> -l<name> -Wl,-rpath,<dir>"` and is callable from SV
   (`br_spawn(0)` → `br_run()` → `br_done()` → `$finish`, output observed).

Nothing about the mechanism is blocked; C1 is pure plumbing over proven pieces.

## In scope
- `zsp_bridge.{h,c}` runtime: `create/destroy/spawn(action_id, seed)/run/done`,
  owning one `zsp_timebase` + allocator + init-ctxt.
- A generated spawn dispatcher (`pssc_bridge_spawn` switch) + `ACTION_*` ids from
  an **explicit action list** (reusing the Phase-C0 `--export-action` mechanism).
- Build `libpssc_scenario.so` and a minimal SV shim (DPI decls + a trampoline
  module that spawns + runs to done).
- A C-harness test (always, gcc-gated) + a Verilator DPI e2e (verilator-gated).

## Out of scope (later phases)
- Imports (C→SV target/solve) — C2/C3, blocked on be-sw import lowering.
- The full `<root>` adapter / `export_api_impl`-over-trampoline behind the
  Phase-C0 interfaces — C4.
- Argument marshalling into action input fields (`zsp_bridge_set_arg`).
- Re-homing the runtime into `zuspec-be-sw` (design §9.1) — see Decision 1.

## Decisions

1. **Bridge runtime lives in `src/pssc/share/c/` for C1** (sibling of the
   `pssc_mem*.h` seam), not yet in `zuspec-be-sw`. It is model-independent and
   `#include`s be-sw's `zsp_timebase.h`/`zsp_init_ctxt.h`/`zsp_alloc.h`. This
   keeps C1 self-contained and testable without editing the vendored be-sw; the
   §9.1 migration to be-sw is a deliberate follow-up once the shape is proven.
2. **Spawn dispatcher is generated by pssc** (`sw_tgt.py`), generalizing
   `_root_harness`: one `case ACTION_<name>:` per listed action, each doing
   `<Action>_init(&ctxt, &root, "root", NULL); <Action>_body(&root, &tb);`. The
   single `pssc_run` is retained as `ACTION_0` / a back-compat wrapper.
3. **New target `sv-dpi-bridge`** (leave today's `sv-dpi` single-`pssc_run`
   facade untouched) that emits the bridge dispatcher + builds the `.so` + emits
   the SV shim. Reuses `--export-action` for the action set; empty list → the
   auto-detected single root as `ACTION_0`.
4. **Seed** flows `zsp_bridge_spawn(id, seed)` → `pssc_solve_all(seed)` when
   runtime-solve is on, preserving today's contract.

## Implementation steps

**D1 — `zsp_bridge.{h,c}` (`src/pssc/share/c/`).** The runtime:
```c
typedef struct zsp_bridge_s zsp_bridge_t;
zsp_bridge_t *zsp_bridge_create(void);
void          zsp_bridge_destroy(zsp_bridge_t*);
void          zsp_bridge_spawn(zsp_bridge_t*, int action_id, long long seed);
void          zsp_bridge_run(zsp_bridge_t*);     /* while(zsp_timebase_run(&tb)){} */
int           zsp_bridge_done(zsp_bridge_t*);    /* !has_pending */
```
The struct owns `zsp_alloc_t`, `zsp_timebase_t`, `zsp_init_ctxt_t`. `spawn`
delegates to a generated `pssc_bridge_dispatch(b, action_id, seed)` (weak/extern)
so `zsp_bridge.c` stays model-independent. *Guard:* compiles against
be-sw `share/include`.

**D2 — generated dispatcher + ids (`sw_tgt.py`).** Add `_bridge_dispatch(actions)`
emitting `pssc_bridge_dispatch.c` (the `ACTION_*` `#define`s + the spawn switch,
reusing the `_root_harness` body shape) and a matching `pssc_bridge_ids.svh`
(`localparam ACTION_* = …`). Resolve the action list via the C0
`_resolve_qualified_name`/auto-detect logic. *Guard:* unit test asserts the
switch + id table for a 2-action model.

**D3 — `.so` build + SV shim (new `SvDpiBridgeTarget`).** Build
`libpssc_scenario.so` from generated `.c` + `zsp_bridge.c` + be-sw `share/rt/*.c`
(+ `pssc_solve.c` when runtime-solve) via `compile_shared`. Emit
`pssc_bridge_pkg.sv`: the `import "DPI-C"` decls (§ design 8), the `ACTION_*`
localparams, and a minimal trampoline module:
```sv
chandle b = zsp_bridge_create();
zsp_bridge_spawn(b, ACTION_Entry, seed);
zsp_bridge_run(b);
while (zsp_bridge_done(b) == 0) zsp_bridge_run(b);
```

**D4 — tests.**
- *C harness* (`tests/unit/test_bridge_c.py`, gcc-gated): generate, build the
  `.so` (or a static exe) with a tiny C `main` calling `create/spawn/run/done`,
  assert the scenario's stdout (`print` → `fprintf`) appears.
- *Verilator DPI e2e* (`tests/sim/sv/test_bridge_e2e.py`, verilator-gated via
  `pytest_dfm` or direct verilator + `-LDFLAGS`): drive the `.so` from the
  trampoline, assert the scenario output + `[TB] done`. Multi-action: spawn two
  ids in sequence, assert both ran.

## Test model
```pss
component pss_top {
    action Hello { exec body { print("hello from C\n"); } }
    action World { exec body { print("world from C\n"); } }
}
```
(`print` in a c-host exec body lowers to `fprintf(stdout, …)` — observable.)

## Risks
1. **`print` lowering in be-sw exec body.** Assumed `fprintf` (seen in prior
   generated output). *Verify in D4*; if absent, use a model whose body has an
   observable effect another way.
2. **dv-solve TU split.** With runtime-solve, `pssc_solve.c` must stay a separate
   TU (the `zsp_alloc.h` conflict). C1's test model is constant/no-rand, so
   solve is a no-op; defer the split exercise to a rand model.
3. **`compile_shared` include/runtime wiring.** Needs `share/include` +
   `share/rt/*.c`. *Verify D3* mirrors the standalone gcc line already proven.

## What C1 covers, and the verified prerequisites for C2–C4

**C1 works for:** any number of explicitly-listed actions, each spawned by id and
run to completion over DPI; **presolved** scenario bodies, **including a spawned
atomic action's own `rand` fields** — baked to a constraint-satisfying value in
the dispatcher (`root.<field> = <v>;` between `_init` and `_body`, via
`solve_action`). Validated on a C harness and Verilator (`x=4` for `3<x<8`).

**Two concrete blockers found by inspecting generated code (2026-06-19) — both are
real codegen features, not configuration:**

1. **Synchronous imports — DONE (2026-06-19), without modifying be-sw.** be-sw
   renders an exec-body import call as `self->do_write(...)` (a struct member that
   does not exist → invalid C). Rather than teach be-sw to declare/bind import
   members, pssc **rewrites the IR call** to a global call
   (`do_write(16, do_read(7))`, `_rewrite_import_calls`), and the generated
   package provides each import as an **`export "DPI-C"` function** the C scenario
   resolves by name at link. The testbench implements `pssc_import_if` and
   registers it (`pssc_set_imports`). Re-entrancy is handled by capturing the SV
   scope (`zsp_bridge_capture_scope`, a `context` import) and `svSetScope`-ing it
   in `zsp_bridge_run` (the §B3 finding); the be-sw async→sync body conversion is
   disabled for the bridge (its dead `_body_sync` mis-renders the global call).
   Build needs `-Wl,--export-dynamic`. Validated on Verilator: `do_read(7)=12`
   flows back into C, which calls `do_write(16,12)` in the testbench.

   **Blocking (time-consuming) target imports — DONE (2026-06-19).** A DPI export
   cannot consume time, so target imports take the request-mailbox path: the
   import call is rewritten to `await self.<import>()`, which makes be-sw emit
   `zsp_timebase_call(&<comp>_<import>_task, …)` + a suspend; a **generated
   sub-task coroutine** marshals the args into a request, posts it
   (`zsp_bridge_post_request` → thread BLOCKED), and on resume returns
   `thread->rval`. The SV trampoline is a **forking event loop**: run → drain
   `next_request` → `fork` the SV import **task** (which may `#`-delay) →
   `complete` (re-wake) → repeat until done. `pssc_import_if` now splits
   target→**task**, solve→**function**. The mailbox lives in `zsp_bridge.c`
   (`post_request`/`next_request`/`complete`/`arg_i`); sub-task prototypes are
   appended to each action's generated header (a global force-include would clash
   with the stale `zsp_thread.h`). Validated on Verilator: a `#10` target task
   fires at **time 10** and the action completes there — i.e. it genuinely
   blocked.

   **Concurrent imports under `parallel` — DONE (2026-06-19).** A top-level
   `parallel { do A; do B; }` export action is detected (`_parallel_branches`) and
   lowered to **fork/join coroutines** (`pssc_bridge_parallel.c`): a
   `pssc_par_<comp>_task` inits `zsp_par_block(N)`, forks one branch per leaf, and
   suspends; each branch constructs its leaf, runs the leaf's (be-sw) `_body_task`
   via `zsp_timebase_call`, then `done_one` + wakes the parent on join. The
   dispatcher spawns this task instead of the sequentially-inlined body; be-sw
   makes `<leaf>_body_task` `static`, so pssc un-statics the called leaves. Both
   leaves' blocking imports post at the same instant → the trampoline forks both →
   genuine concurrency. Validated on Verilator: two `#10` imports both fire at
   **time 10** (not 10 & 20). *Out of scope:* wide-vector/struct marshalling
   (scalar `int`/`longint`); rand in parallel leaves; nested
   `parallel`/`select`/`schedule` (single top-level `parallel` of atomic leaves
   covered).
2. **A spawned action's own rand fields — DONE for presolve (2026-06-19).** The
   dispatcher now bakes constraint-satisfying values via `solve_action`
   (`_presolved_field_assigns`), covering top-level scalar rand fields.
   **Per-spawn runtime solve — DONE (2026-06-19).** `--runtime-solve` emits a
   `pssc_solve.c` dv-solve TU (compiled separately, then linked `-ldv_solve` — the
   `zsp_alloc.h` conflict avoided by the TU split, design §9) and the dispatcher
   calls `pssc_solve_all((unsigned long long)seed)` then injects `root.<f> =
   g_<prefix><f>`. Validated: a C harness and **Verilator** produce
   constraint-satisfying, seed-varying values (`3<x<8`: seed1→5, 2→6, 3→7…).
   *Remaining:* nested/array rand fields (top-level scalars covered).

   **Seed source — verified + wired (2026-06-19).** Verilator 5.041 supports
   `process::self().get_randstate()` and `$urandom`/`$urandom_range`, and
   `{$urandom, $urandom}` is reproducible under `+verilator+seed+N`. The generated
   package exposes `pssc_run_action_rand(b, id)`, which draws the seed from the
   calling process's PRNG — so per-spawn solving is reproducible under the
   testbench seed (validated e2e).

Next decision point: **#1 (imports)** is be-sw codegen work (declare + bind import
function pointers); the remaining rand work is pssc-local. Recommend the runtime-
solve slice next (pssc-local, makes spawns honor the `seed`) before the be-sw
import work.
